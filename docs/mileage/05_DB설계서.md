# 마일리지·뱃지 DB 설계서

- 대상: momoai.kr (Flask + SQLAlchemy + Jinja2)
- 근거 문서: `01_마일리지_운영정책.md`, `00-codebase-survey.md`

---

## 1. 설계 원칙

### 1.1 잔액이 아니라 이력을 저장한다

회원 테이블에 `points` 컬럼을 두고 더하고 빼지 않는다. 모든 적립·취소를 `point_events` 테이블에 **한 줄씩 기록**하고, 현재 점수는 합계로 계산한다.

- 월간 점수와 누적 점수를 같은 테이블에서 조건만 바꿔 집계할 수 있다
- "이 점수가 왜 이렇죠?"라는 문의에 근거를 보여줄 수 있다
- 잘못 지급해도 취소 기록을 한 줄 더 쌓으면 되고, 과거를 지우지 않는다

### 1.2 중복 지급은 DB가 막는다

코드로만 막으면 반드시 새어 나간다. `(학생, 활동코드, 대상종류, 대상ID, 기록종류)` 조합에 **유니크 제약**을 걸어, 같은 첨삭 하나에 두 번 지급하는 것이 DB 레벨에서 불가능하게 한다.

### 1.3 점수 값은 코드 상수로 관리한다

적립 점수와 상한은 DB가 아니라 `app/services/mileage_rules.py`의 상수 딕셔너리에 둔다. 점수를 바꿀 때 마이그레이션이 필요 없고, 과거 적립 이력은 이미 `point_events`에 확정된 값으로 남아 있어 소급 변경되지 않는다.

### 1.4 시간 처리

- 저장은 UTC (`datetime.utcnow()`) — 기존 모델 관행을 따른다
- 화면 표시는 기존 `kst` Jinja 필터
- **시즌(월) 판정은 KST 기준**으로 계산한다. UTC로 계산하면 매월 1일 오전 9시 이전 활동이 전월로 잡힌다

### 1.5 집계 캐시 테이블은 만들지 않는다

현재 학생 수 규모에서는 `point_events` 합계 쿼리로 충분하다. 캐시 테이블을 두면 실제 이력과 캐시가 어긋나는 버그가 반드시 생긴다. 느려지면 그때 추가한다.

## 2. 테이블 설계

모델은 `app/models/mileage.py` 한 파일에 정의한다. FK 컬럼 타입은 **참조 대상 테이블의 PK 타입과 반드시 일치**시킨다(예: `students.student_id`, `users.user_id`).

### 2.1 point_events — 포인트 원장

| 컬럼 | 타입 | 설명 |
|---|---|---|
| event_id | Integer PK | 자동 증가 |
| student_id | FK students | 포인트 귀속 학생 |
| activity_code | String(10) | RW01, QZ01, CM01 등 |
| entry_type | String(10) | `award`(적립) / `cancel`(취소) |
| points | Integer | 적립은 양수, 취소는 음수 |
| status | String(10) | `pending` / `confirmed` / `cancelled` |
| source_type | String(30) | essay, post, comment, quiz_session, attendance_week, attendance_quarter, manual |
| source_id | String(64) | 대상 레코드의 ID (문자열로 통일 저장) |
| season | String(7) | `2026-09` (KST 기준) |
| occurred_at | DateTime | 활동 발생 시각 (UTC) |
| confirmed_at | DateTime | 확정 시각, nullable |
| cancelled_at | DateTime | 취소 시각, nullable |
| cancel_reason | String(200) | 취소 사유, nullable |
| related_event_id | Integer FK self | 취소 기록이 가리키는 원본 적립 기록 |
| granted_by | FK users | 수동 지급자, nullable |
| memo | String(200) | 관리자 메모, nullable |
| created_at | DateTime | 생성 시각 (UTC) |

**제약**
- `UniqueConstraint(student_id, activity_code, source_type, source_id, entry_type)` — 이름 `uq_point_event_source`
- 인덱스: `(student_id, season)`, `(season, status)`, `(source_type, source_id)`

**status 흐름**
```
pending ──(확정 배치)──> confirmed ──(취소)──> cancelled
   └────(확정 전 삭제)──> cancelled
```
취소 시에는 원본 행의 `status`를 `cancelled`로 바꾸고, **동시에 `entry_type='cancel'`인 음수 행을 새로 추가**한다. 합계 계산은 `status != 'cancelled'`인 행만 더하면 되고, 이력은 그대로 남는다.

### 2.2 badges — 뱃지 정의

| 컬럼 | 타입 | 설명 |
|---|---|---|
| badge_code | String(10) PK | BG01 ~ BG10 |
| name | String(50) | 첫 문장, 첫 물음표 … |
| description | String(200) | 달성 조건 안내 문구 |
| category | String(10) | 초급 / 중급 / 고급 / 최종 |
| icon_path | String(200) | 아이콘 파일 경로 |
| sort_order | Integer | 수집판 표시 순서 |
| is_repeatable | Boolean | 반복 획득 가능 여부 |
| rule_type | String(30) | first_event, count_threshold, external_metric, manual, all_badges |
| rule_config | Text(JSON) | 판정에 필요한 값 |
| is_active | Boolean | 사용 여부 |

뱃지는 **정의를 데이터로 관리**한다. 조건을 바꾸거나 새 뱃지를 추가할 때 코드를 고치지 않기 위해서다.

`rule_config` 예시
```json
{"activity_code": "RW01", "threshold": 1}
{"metric": "received_likes", "threshold": 100, "or_metric": "received_comments", "or_threshold": 50}
{"metric": "quarter_completed", "threshold": 4}
```

### 2.3 student_badges — 뱃지 획득 이력

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | Integer PK | |
| student_id | FK students | |
| badge_code | FK badges | |
| earned_count | Integer | 반복 획득 횟수, 기본 1 |
| first_earned_at | DateTime | 최초 획득 (UTC) |
| last_earned_at | DateTime | 최근 획득 (UTC) |
| granted_by | FK users | 수동 수여자, nullable |
| revoked_at | DateTime | 회수 시각, nullable |

**제약**: `UniqueConstraint(student_id, badge_code)`

### 2.4 monthly_rankings — 월간 랭킹 확정 스냅샷

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | Integer PK | |
| season | String(7) | 2026-09 |
| level_group | String(20) | 학년 또는 레벨 구분값 |
| student_id | FK students | |
| rank | Integer | 순위 |
| points | Integer | 확정 시즌 점수 |
| is_final | Boolean | 확정 여부 |
| created_at | DateTime | |

**제약**: `UniqueConstraint(season, level_group, student_id)`

순위는 **매번 계산하지 않고 확정 시점에 저장**한다. 실시간 계산으로 보여주면 나중에 점수가 취소될 때 과거 순위가 소급 변경된다.

### 2.5 mileage_consents — 공개 동의 이력

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | Integer PK | |
| student_id | FK students | |
| consent_type | String(1) | A(랭킹 공개) / B(앱 내 게시) / C(홍보물 활용) |
| is_agreed | Boolean | |
| agreed_by_user_id | FK users | 동의한 계정 |
| agreed_by_relation | String(10) | self / parent |
| doc_version | String(10) | 동의서 버전 |
| agreed_at | DateTime | |
| revoked_at | DateTime | 철회 시각, nullable |

동의는 **항목별로 따로 저장**하고, 변경 시 기존 행을 수정하지 않고 새 행을 추가한다. 분쟁 시 "언제 누가 무엇에 동의했는가"를 증명해야 하기 때문이다.

### 2.6 기존 테이블 변경

| 테이블 | 변경 | 이유 |
|---|---|---|
| comments | `is_deleted` Boolean, `deleted_at` DateTime 추가 | 삭제된 댓글의 포인트 회수 처리. 현재 실삭제 구조라 회수 근거가 사라짐 |

## 3. 활동 코드와 데이터 매핑

| 코드 | 활동 | source_type | 원천 데이터 | 지급 시점 |
|---|---|---|---|---|
| RW01 | 리라이팅 | essay | `Essay.is_finalized = True` | 첨삭 확정 즉시 confirmed |
| EX01 | 우수답안 | essay / post | 관리자 선정 액션 | 선정 즉시 confirmed |
| QZ01 | 퀴즈 응시 | quiz_session | `*QuizSession.score >= 60` | 세션 완료 즉시 confirmed |
| QZ02 | 퀴즈 만점 | quiz_session | `score = 100` | 세션 완료 즉시 confirmed |
| QS01 | 질문 등록 | post | `Post.category = 'question'` | pending → 24시간 후 confirmed |
| QS02 | 우수질문 | post | 관리자 선정 액션 | 선정 즉시 confirmed |
| CM01 | 댓글 | comment | `Comment` 생성 | pending → 24시간 후 confirmed |
| AT01 | 주간 출석 | attendance_week | `Attendance` 주간 집계 | 주간 배치에서 confirmed |
| AT02 | 분기 완주 | attendance_quarter | `Attendance` + `SessionAdjustment` | 분기 배치에서 confirmed |
| EV01 | 재량 지급 | manual | 관리자 입력 | 즉시 confirmed |

`source_id`는 각각 `essay_id`, `session_id`, `post_id`, `comment_id`, `{student_id}-{연도}-W{주차}`, `{student_id}-{연도}Q{분기}` 형태의 문자열로 만든다. 주간·분기 항목은 실제 레코드가 없으므로 **조합 키를 문자열로 만들어 중복 지급을 막는다.**

## 4. 서비스 계층 구조

```
app/services/
  mileage_rules.py     점수·상한 상수 (POINT_RULES, BADGE_RULES)
  mileage_service.py   적립·취소·조회 함수
  badge_service.py     뱃지 판정·부여
  ranking_service.py   랭킹 집계
```

라우트에서 직접 `point_events`에 INSERT 하지 않는다. 반드시 `mileage_service.award_points()`를 거치게 해서 상한 검사와 중복 방지를 한 곳에서 처리한다.
