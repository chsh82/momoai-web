## 0. 배포 전 코드 작업 — 시작일 게이트

9월 1일부터 적립하기로 했으므로, 그 전에 배포하면 8월 활동에 점수가 붙습니다. 코드에 시작일 잠금을 넣어야 합니다.

아래를 클로드 코드에 붙여넣어 먼저 처리한다.

--- 프롬프트 시작 ---

마일리지 적립 시작일 게이트를 구현한다. 기능은 배포하되 2026년 9월 1일 이전 활동에는 포인트가 부여되지 않아야 한다.

1. `app/services/mileage_rules.py`에 상수를 추가하라.
```python
MILEAGE_START_DATE = date(2026, 9, 1)   # KST 기준
```

2. `award_points()` 진입부에서 게이트를 검사하라.
   - `occurred_at`(없으면 현재 시각)을 KST로 변환한 날짜가 `MILEAGE_START_DATE` 이전이면 아무것도 하지 않고 `None`을 반환한다
   - 반환 전에 debug 레벨 로그를 남긴다
   - 예외를 던지지 말 것. 기존 라우트의 try/except를 거치더라도 조용히 넘어가야 한다

3. 주간 출석 배치(AT01)는 **9월 7일 시작 주부터** 집계하라.
   - 8월 31일~9월 6일 주는 시작일 이전 수업이 섞여 있으므로 건너뛴다
   - 배치에서 대상 주의 시작일이 `MILEAGE_START_DATE`보다 이르면 처리하지 않고 로그만 남긴다

4. 분기 완주 배치(AT02)는 시작일과 분기 시작이 일치하므로 별도 처리가 필요 없다.
   (4분기 = 9~11월, 첫 지급은 12월 1일 배치)

5. 게이트가 동작하는지 확인 스크립트를 작성하라.
   - 8월 31일자 활동 → 적립되지 않음
   - 9월 1일자 활동 → 정상 적립
   - 9월 3일 시작 주 배치 → 건너뜀
   - 9월 7일 시작 주 배치 → 정상 집계

6. 이 상수는 나중에 삭제할 수 있도록 한 곳에만 두고, 참조 위치를 보고하라.

## 2. 운영 배포 절차

### 2-1. 백업 (필수)

```bash
# 운영 서버 접속 후
cd <프로젝트 경로>
cp instance/momoai.db instance/momoai.db.bak_before_mileage_$(date +%Y%m%d_%H%M%S)
ls -lh instance/*.bak_*
```

파일 크기가 원본과 같은지 확인한다. 이 백업이 유일한 되돌리기 수단이다.

### 2-2. 코드 배포

평소 배포 절차(GitHub Actions 등)를 그대로 사용한다.

### 2-3. 마이그레이션 적용 (수동)

```bash
# 현재 상태 확인
flask db current
flask db heads

# 적용
flask db upgrade

# 결과 확인
flask db current   # b7c1f2a9d4e0 이어야 함
```

`flask db upgrade`가 실패하면 **즉시 중단하고 4번 롤백 절차로 간다.** 부분 적용된 상태에서 재시도하지 않는다.

### 2-4. 뱃지 시드

```bash
python scripts/seed_badges.py
```

10개 뱃지가 들어갔는지 확인한다. 이걸 빠뜨리면 학생 화면의 수집판이 빈 채로 나온다.

**최초 배포가 아닌 경우(5단계 이후)는 이어서 아래 두 개를 실행한다.**

### 2-5. 뱃지 정의 갱신

```bash
python scripts/update_badges_essay_type.py
```

BG01·BG03·BG07의 판정 조건과 임계값을 갱신한다. 멱등이라 여러 번 실행해도 안전하다.

### 2-6. BG01 소급 부여 (알림 없이)

```bash
python scripts/backfill_bg01_badge.py
```

기존 과제가 있는 학생에게 「첫 문장」 뱃지를 조용히 부여한다.

> **순서를 반드시 지킬 것.** 이 스크립트는 **배포 직후, 다음 야간 뱃지 스윕 배치(매일 03:00)가 돌기 전에** 실행해야 한다. 순서가 밀려 야간 배치가 먼저 돌면 알림이 켜진 상태로 부여되어, 재원생 200명 가까이가 한꺼번에 뱃지 알림을 받는다. **한 번 나간 알림은 회수할 수 없다.**
>
> 03:00 직전에 배포하게 된다면, 배포를 다음 날로 미루거나 스윕 job을 일시적으로 꺼두고 진행한다.

### 2-7. 애플리케이션 재시작

스케줄러가 새 job 6개와 함께 뜬다. 로그에서 job 등록을 확인한다.

## 3. 배포 직후 확인

| 순서 | 확인 항목 |
|---|---|
| 1 | 기존 기능이 정상인가 — 첨삭 저장, 퀴즈 응시, 댓글 작성·삭제 |
| 2 | 학생 계정으로 마이페이지 접속 — 0점 상태 화면이 안내와 함께 보이는가 |
| 3 | 뱃지 수집판에 10칸이 조건과 함께 보이는가 |
| 4 | 랭킹 페이지 — "아직 집계되지 않았어요" 안내가 보이는가 |
| 5 | 학부모 계정으로 자녀 마일리지 조회 |
| 6 | 강사 계정으로 우수답안 선정 버튼과 잔여 횟수 표시 |
| 7 | 관리자 모니터링 화면 접속 |
| 8 | 스케줄러 로그에 job 6개 등록 확인 |

**1번이 가장 중요합니다.** 마일리지는 없어도 학원이 돌아가지만, 첨삭과 댓글이 깨지면 당장 업무가 멈춥니다.

배포 후 하루 동안은 로그에서 `마일리지` 관련 예외가 찍히는지 지켜본다. 적립 호출은 전부 try/except로 감싸여 있어 기존 기능을 막지는 않지만, 예외가 반복되면 원인을 찾아야 한다.

## 4. 롤백 절차

문제가 생기면 **코드만 되돌린다. 마이그레이션은 되돌리지 않는다.**

새로 만든 5개 테이블은 기존 기능과 무관하므로 남아 있어도 아무 영향이 없다. 반면 `downgrade`로 테이블을 지우면 그때까지 쌓인 데이터가 사라지고, `comments.is_deleted` 컬럼이 빠지면서 댓글 조회가 깨진다.

```bash
# 코드만 이전 커밋으로 되돌리고 재시작
```

스케줄러 job만 끄고 싶다면 `app/utils/scheduler.py`에서 마일리지 job 등록 부분을 주석 처리하고 재시작한다.

DB 자체를 되돌려야 하는 최악의 경우에만 2-1의 백업 파일을 사용한다. 이 경우 배포 이후 쌓인 모든 데이터(첨삭, 댓글, 출결 등)가 함께 사라지므로, 마지막 수단이다.
